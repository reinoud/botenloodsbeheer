# Terugblik Aegis, security-review #348

Datum: 2026-11-20. Taak: security-review van de gestagede wijziging voor #348 (laatste beheerder die kan inloggen).

## Wat ging goed

De brief noemde de vergrendeling, de bestaande tests en de mutanten die de regie al had gedraaid. Daardoor kon ik me richten op de vraag die overbleef: welke andere route haalt de laatste inlogmethode van een collega weg terwijl iemand zichzelf kijker maakt.

## Wat kon beter

De brief zei niet of `rol_wijzigen` ook via de API of de CLI bereikbaar is. Dat moest ik zelf nagaan; het antwoord (alleen de webroute, met recente inlog) bepaalt of een actor zonder inlogmethode kan bestaan.

## Wat deed je zelf goed

Ik heb alle plekken nagelopen die een inlogmethode weghalen (`herstellen`, `methode_intrekken`, `verwijderen`, het opnieuw hashen van een wachtwoord) en per plek vastgesteld of die onder hetzelfde slot valt. Ik heb alleen de gerichte tests gedraaid (9 geslaagd, 0 overgeslagen), niet de hele suite.

## Wat heb je onderweg zelf verbeterd

Eerst wilde ik een racetest voor `herstellen` tegen `rol_wijzigen` voorstellen. Dat heb ik geschrapt: beide nemen `FOR UPDATE` op alle actieve accounts, dus het slot dekt het al, en een extra test past niet bij het risico.

## Wat kan structureel beter

Zet in de opdracht: noem per gereviewde domeinfunctie via welke ingangen (web, API, CLI) ze bereikbaar is.
