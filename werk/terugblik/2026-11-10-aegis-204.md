# Terugblik Aegis, securityreview #204, #207 en #212

Datum: 2026-11-10
Taak: securityreview van de gestagede diff op `feature/204-eigenaar-onbekend` (eigenaar onbekend, knop Nieuwe boot, veld `clubboot` in de API). Oordeel: akkoord, met vier adviespunten.

## Wat ging goed

De brief scheidde de securityrelevante paden van CSS en documentatie en noemde per sjabloon waar het wordt ingevoegd. Daardoor kon ik gericht lezen: routes, domeinregels, CSV-regel, API en migratie. De issues bevatten de besluiten van de stakeholder, zoals de uitzondering op de wachtlijst, zodat ik die niet als bevinding hoefde te melden.

## Wat kon beter

Mijn live proef via de proxy (eigen beheerder `aegis204`, getekende sessie, CSRF-weigering naast een geldige aanvraag op een id die niet bestaat) werd door de toestemmingslaag geweigerd, omdat een beheerder aanmaken in de gedeelde container telt als wijziging van een gedeelde bron. De overlay staat dat toe, de omgeving niet. Het oordeel steunt daardoor alleen op de code en de tests.

## Wat deed ik zelf goed

Ik heb de rechten op de nieuwe kolom met een leesquery op `information_schema.column_privileges` gecontroleerd in plaats van alleen de migratie te lezen. Ik heb ook nagelopen of een ander pad een lid van een boot kan halen (opschonen, FK zonder `ondelete`), omdat zo'n pad een boot stil in de toestand onbekend zou zetten.

## Wat heb ik onderweg verbeterd

Na de weigering heb ik niet geprobeerd de proef via een andere weg toch te draaien, maar de CSRF-dekking statisch vastgesteld: `CSRFProtect` voor de hele app, alleen de API vrijgesteld, en het sjabloon met `_csrf.html`.

## Wat kan structureel beter

Zet in de opdracht: "Een live proef met een eigen beheerder in de container `web` vraagt vooraf toestemming in de omgeving; zonder die toestemming toetst aegis CSRF en autorisatie statisch en meldt dat in het oordeel."
