# Terugblik Aegis, securityreview #178

Datum: 2026-11-08
Taak: securityreview van de gestagede koppeling met e-boekhouden in de integratiecontainer (issue #178).

## Wat ging goed

De opdracht noemde de aandachtspunten per risico (inloggegevens, record, tekst van de bron, schrijfdoel, supply chain, netwerk). Daardoor kon ik de diff gericht doorlopen. De code zelf maakte het makkelijk: één bestand voor e-boekhouden, foutafhandeling op één plek, en tests die de geheimen in het log en in de fout al controleren.

## Wat kon beter

Het filter op `Def2` ("bevat actief") staat zowel in ADR-004 als in de code, maar nergens staat welke waarden e-boekhouden in de praktijk kent. Dat moest ik uit het oude voorbeeldproject halen (`actief_gewoon`, `actief_partner`, `actief_jeugdlid`). Een lijst van echte waarden had het oordeel over het filter zekerder gemaakt.

## Wat deed ik zelf goed

Ik heb de WSDL op imports gecontroleerd (geen, dus geen netwerk bij het laden), het gedrag van zeep tegen XXE en de logniveaus nagelopen, en gekeken of de inloggegevens via een `env_file` in andere containers terechtkomen. Ik bleef proportioneel: drie adviespunten, geen blokkade.

## Wat heb ik onderweg zelf verbeterd

Eerst dacht ik dat het filter op een deel van het woord een bevinding van belang was ("inactief" bevat "actief"). Na het voorbeeldproject heb ik het teruggezet naar een adviespunt met een lage zekerheid, omdat de bekende waarden met `actief_` beginnen.

## Wat kan structureel beter in de opdracht of de afspraken

Zet in de opdracht: "Noem bij een filter op data uit een externe bron de waarden die in de praktijk voorkomen, of zeg dat ze onbekend zijn."
